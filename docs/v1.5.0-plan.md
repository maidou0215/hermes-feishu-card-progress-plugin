# v1.5.0 实现计划 — 回复渲染质量 + 鲁棒性

> 主题：不改架构（仍是 monkey-patch），提升最终回复的渲染完整性与运行鲁棒性。
> 借鉴来源：[Cheerwhy/hermes-lark-streaming](https://github.com/Cheerwhy/hermes-lark-streaming)、hermes-feishu-streaming-card。
> 调研于 v1.4.0 发布后（2026-06-19）。

## 范围

### 核心三件（必做）

#### 1. 图片解析（markdown img → 飞书 img_key）

**问题**：AI 回复含 markdown 图片 `![](url)` 时，飞书卡片不能直接显示外链图，渲染成文本链接，体验差。

**方案**：
- 在 `_patched_send` / `_build_outbound_payload` 拦截最终回复文本
- 正则提取 `![alt](url)`，下载图片，调用飞书素材上传 API 换 `img_key`
- 替换为飞书卡片图片元素
- 异步处理 + 失败回退（上传失败则保留原链接）

**复杂度**：中（下载 / 上传 / 缓存 / 异步）

#### 2. 卡片 200 元素通用拆分

**问题**：当前仅处理 5 表格限制（`_split_content_by_tables`）。长对话或多工具场景，卡片元素总数接近飞书 200 上限会发送失败。

**方案**：
- 扩展拆分逻辑：除表格外，计数所有卡片元素（文本块 / 代码块 / 分隔线 / 工具面板等）
- 接近上限时按元素边界拆分为多张卡片
- 旧卡片封存（数据完整），新卡片继续，仅最后一张带 footer
- 复用现有 `FEISHU_PROGRESS_TABLE_OVERFLOW` 机制或新增元素上限配置

**复杂度**：中（复用现有 split 架构）

#### 3. 消息保护（撤回 / 删除终止更新）

**问题**：用户撤回 / 删除消息后，插件仍在 PATCH 已删除的卡片，产生无效 API 调用和错误日志。

**方案**：
- 监听消息删除 / 撤回事件
- 清理对应 chat_id 的卡片状态（`_active_cards` 等）
- 停止后续 PATCH

**复杂度**：低

### 不做（留 v2.0）

- **流式文本输出（打字机）** —— 最大体验差距，但需迁移到飞书 CardKit v2.0 流式 API（放弃手动 PATCH），架构级演进，单独大版本。

### Stretch（视精力）

- footer 配置化（env var 控制字段 / 标签 / 文字大小）
- 中断处理（`/stop` + 消息打断 + 中断态卡片）

## 验收标准

- 图片解析：AI 回复含图时卡片正确显示图片（非链接）
- 200 元素拆分：超长回复自动拆卡，不报错
- 消息保护：撤回消息后无无效 PATCH、无错误日志
- 现有功能回归（footer / think / 表格拆分 / PATCH 锁）不受影响
- unittest 覆盖新增逻辑
